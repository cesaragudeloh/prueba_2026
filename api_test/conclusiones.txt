Hallazgos y conclusiones del ejercicio

1. Se implemento correctamente el flujo CRUD de usuario sobre Petstore con orden estricto: crear, buscar, actualizar, buscar actualizado, eliminar y verificar 404 final.
2. El flujo principal quedo consolidado en `src/test/resources/features/users/crud-flow.feature`, usando el mismo usuario durante toda la ejecucion.
3. Se mantuvieron features individuales (`create`, `read`, `update`, `delete`) para cobertura por operacion, y el runner ejecuta la suite completa de `features/users`.
4. Se mejoro la trazabilidad en consola:
   - Logging global formateado desde `karate-config.js`.
   - Impresion explicita de request/response en el flujo E2E con `karate.pretty(...)` y etiquetas por operacion.
5. Se reemplazaron valores genericos por datos de prueba mas realistas (`John Doe`, `Jane Smith`, etc.).
6. Se acorto el formato de `username` para mejorar legibilidad en consola y reportes: `qa` + `(System.currentTimeMillis() % 100000)`.
7. El `user.json` se mantiene como plantilla reutilizable y cada escenario sobrescribe campos dinamicos (id, username, email, nombres, etc.).
8. La ejecucion validada con Gradle fue satisfactoria (`./gradlew test`), generando reportes HTML para evidencias.
9. Riesgo residual: al usar un endpoint publico (`https://petstore.swagger.io/v2`), pueden existir respuestas intermitentes por disponibilidad del servicio.
10. Recomendacion final: para CI/CD estable, considerar retries controlados y opcion de entorno mock/stub para pruebas deterministicas.
